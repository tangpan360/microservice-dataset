# 方案设计

## 核心目标

本方案面向 Train-Ticket 的混合业务负载注入，重点解决两个问题：

- 业务行为要足够真实，能够触发稳定的后端调用链
- 负载强度要可控，能够按时间阶段与比例复现

因此实现上采用三层结构：

- 动作层：描述最小业务动作
- 场景层：组织动作顺序和参数策略
- 混合层：定义不同阶段的场景比例与负载强度

## 分层说明

### 动作层

动作层只关心“做一件事”，例如：

- 查询余票
- 查询路线
- 查询食物
- 创建订单
- 支付订单
- 取消订单
- 取票
- 进站
- 改签
- 托运
- 管理观察

动作层不负责：

- 长流程业务编排
- 全局负载控制
- 压测阶段切换

### 场景层

场景层负责表达一个完整业务意图，例如：

- 浏览
- 高级规划浏览
- 订单刷新或联系人查询
- 下单并支付
- 带餐食或带保险下单
- 支付后取票并进站
- 取消
- 改签
- 托运
- 管理观察

场景层只处理：

- 动作执行顺序
- 参数选择
- 必要的前置状态准备

### 混合层

混合层通过 YAML 表达多个阶段：

- 每个阶段持续多久
- 每个阶段多少用户
- 每个阶段各场景占比是多少

运行时由 `Locust` 读取这些配置，按当前时间选择阶段，再从该阶段的 `mix` 中抽取场景执行。

## 当前定稿方向

当前版本将场景固定为四类：

- 浏览类：提供稳定背景流量
- 支撑类：补足订单查看、联系人、餐食浏览等常用轻操作
- 交易类：提供真正会引起状态变化的业务链路
- 观察类：补充少量后台读流量

这样做的目标是：

- 保持核心交易链路完整
- 避免只靠重交易场景构造负载
- 让后续容量实验和预测数据更接近真实混合业务
- 控制场景总量，便于长期维护

## 为什么不用“脚本集合”方式

如果只保留一组零散脚本，会遇到这些问题：

- 场景入口靠文件名驱动，难扩展
- 前置状态准备容易散落在不同脚本里
- 很难稳定接入 `Locust` 或其他负载发生器
- 很难用统一配置表达混合场景

本方案把这些问题收敛到：

- 注册表统一管理场景 ID
- 核心库统一管理登录、HTTP、前置订单准备
- `Locust` 只负责调度，不承担业务细节

## 当前实现边界

当前版本优先保证：

- 结构干净
- 场景清晰
- 代码可运行
- 能直接接入后续数据采集流程

暂不追求：

- 对所有 Train-Ticket 服务做全量覆盖映射
- 做复杂的 UI、报表或 trace 导出工具
- 做面向其他 benchmark 的通用框架
- 把所有后台写操作和外围冷门服务都放进第一版主场景目录
