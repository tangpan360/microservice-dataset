# 运行与采集

推荐把本方案和 Prometheus 指标采集配合使用。

## 最小运行流程

1. 部署 Train-Ticket 与监控组件
2. 准备普通用户和管理员账号
3. 选择一个混合配置文件
4. 先执行单场景 dry-run
5. 再执行 `Locust` 混合压测
6. 按统一时间窗导出服务级指标

## 单场景验证

建议先逐个验证关键场景，例如：

```bash
TT_BASE_URL="http://localhost:8080" \
python -m tt_injector.cli.dryrun browseBasic
```

如果要验证订单相关场景：

```bash
TT_BASE_URL="http://localhost:8080" \
python -m tt_injector.cli.dryrun preserveAndPay
```

建议优先验证以下几类场景：

- 浏览类：`browseBasic`、`browseAdvanced`
- 支撑类：`orderRefresh`、`contactLookup`
- 交易类：`preserveAndPay`、`preserveWithFood`、`preserveWithAssurance`、`rebookFlow`
- 观察类：`adminObserve`

如果要快速检查动作层和关键前置状态是否正常，可执行：

```bash
TT_BASE_URL="http://localhost:8080" \
python -m tt_injector.cli.check_actions
```

这个检查会覆盖：

- 基础查询与高级规划
- 餐食查询
- 订单刷新
- 普通下单与高铁下单
- 带餐食下单与带保险下单
- 支付、取消、取票、进站、改签、托运
- 后台基础查询

## Locust 运行示例

```bash
cd benchmarks/trainticket/load_injector
TT_BASE_URL="http://localhost:8080" \
TT_MIX_CONFIG="configs/mix/steady.yaml" \
locust -f "src/tt_injector/adapters/locust/locustfile.py" --headless
```

## 推荐采集方式

每次实验建议绑定一个唯一 `run_id`，并固定以下信息：

- 应用版本
- 混合配置
- 副本数
- 指标采样间隔
- 是否启用服务网格
- 当前使用的场景目录版本

建议至少采这些字段：

- `service_rps_1m`
- `service_cpu_usage_cores`
- `service_mem_working_set_bytes`
- `service_replicas_ready`
- `service_latency_p95`

如果开启服务网格，还建议采：

- `edge_rps_1m`
- `edge_latency_p95`

## 结果组织建议

- 一次运行对应一个 `run_id`
- 混合配置与导出结果一起归档
- 保持统一时间粒度，便于后续训练与复现
